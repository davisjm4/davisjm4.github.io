Learn / Reference — TCP and UDP

What a transport protocol does

IP moves packets between devices across the Internet. A transport protocol runs on top of IP and delivers data between programs on those devices. TCP and UDP are the two most common transport protocols. Neither is better in general: an application picks the one whose behavior matches what it needs, and protocols built on top can add more.

The table describes built-in behavior. It does not make one protocol better than the other: an application or a protocol layered above UDP can add reliability, ordering and security itself.

TCP

TCP is connection-oriented: the two ends set up a connection with a three-way handshake before data flows, and both keep track of it. It delivers a byte stream: it numbers the data, uses acknowledgments to detect losses, retransmits lost segments and hands bytes to the application in their original order. Delivery is reliable while the connection works; if the network fails completely, data cannot arrive. A detected connection failure can be reported to the application, but detection can take time. A transport acknowledgment does not confirm that the receiving application completed an action. Flow control keeps a fast sender from overwhelming a slow receiver, and congestion control slows the sender when the network is congested.

TCP does not keep message boundaries, so applications that send separate messages over it mark where each one ends. TCP does not encrypt; encryption comes from TLS running above it.

UDP

UDP is connectionless: a program sends a datagram without any setup, and each datagram is delivered as a separate unit with its boundaries kept. UDP has no built-in guarantee that a datagram arrives or arrives in order, and it never retransmits. Its header is small (8 bytes), and it has no flow or congestion control, so applications that send a lot of data over it should adjust their own rate. UDP can also send one datagram to a broadcast or multicast address.

Because UDP adds so little, applications can build exactly the behavior they need on top of it: their own acknowledgments, repair data, or recovery only for important messages. UDP is not insecure by nature; protocols such as DTLS and QUIC encrypt data carried over it.

Reliability versus timeliness

Retransmission and in-order delivery have a cost: when one piece is lost, everything after it waits until the piece is resent. This is called head-of-line blocking. For a file or a bank transaction, waiting is right because every byte matters. For live voice, video or game positions, data that arrives late is useless, so skipping a lost piece and using the newest data keeps the experience responsive. A large delay budget, such as a livestream that runs 20 seconds behind, gives time to recover lost data, so “live” does not automatically mean UDP.

Network overhead and connections

TCP’s handshake costs a round trip before any data is sent, and its header is larger. That overhead matters for tiny messages and one-question exchanges, and matters little for a connection that stays open and carries a lot of data. Small size alone does not decide: a tiny message that must not be lost may still call for TCP.

Protocols in use today

HTTP/1.1 and HTTP/2 run over TCP. QUIC runs over UDP and provides reliability, congestion control, encryption and independent streams itself, so a loss in one stream does not stall the others. HTTP/3 runs over QUIC, so not all web traffic uses TCP; browsers fall back to HTTP/2 over TCP when a network blocks QUIC. DNS commonly uses UDP for ordinary small lookups and uses TCP for answers too large for the first reply and for zone transfers; DNS servers are expected to support both. Streaming does not automatically mean UDP either: much on-demand video is delivered over HTTP on TCP or QUIC.

How to decide

  • Does the application rely on the transport to recover every byte, in order? That points to TCP.
  • Is late data useless, and does the application skip or handle missing data itself? That points to UDP.
  • Does a named protocol fix the transport (HTTP/2, SSH, QUIC, HTTP/3, DNS)? Then the protocol decides.
  • Does the application need one message to reach many devices, or must its session survive an address change? That points to UDP.
  • Never decide from the type of application alone: games, video and sensors appear with both answers.
