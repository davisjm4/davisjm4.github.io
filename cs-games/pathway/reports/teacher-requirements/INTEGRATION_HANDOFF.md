## Mounting the editor in the redesigned pathway editor

Add a panel (or a tab) to the class pathway editor and mount the component into it:

```js
import { createRequirementsEditor } from '../requirements/editor.mjs';
import { createServiceAdapter } from '../requirements/adapter.mjs';

const adapter = createServiceAdapter({ request, token, entry });   // the editor's own request(), token and entry object
const editor = createRequirementsEditor(panelElement, {
  graph, registry,                       // curriculum-graph.json and evidence-gap-registry.json
  pathway: entry.draft, published: entry.published ?? null,
  adapter, tab: 'class',
  theme: document.documentElement.dataset.theme === 'light' ? 'light' : null,
  onChange: (next) => { entry.draft = next; /* then the editor's own persist()/render() */ },
});
```

- Load `requirements.css` after the site stylesheet. All rules are under `.mreq` and read the site tokens with fallbacks.
- `createServiceAdapter` makes the calls the existing pacing editor already makes: `request('/pathways/teacher/<id>/draft', { token, body: { pathway, draftVersion } })`, then `.../preview`, then `.../publish` with the preview token, and it keeps `entry.draftVersion` current. It adds no endpoint.
- **When the editor is not connected to the shared service** (local-only mode), pass your own local adapter with the same three methods, or `createMemoryAdapter` for a throwaway session. The component never touches browser storage itself; the host persists `onChange` output however it already persists drafts.
- After a publish, replace the host's `entry.published` and `entry.draft` with what the adapter returned (the editor already updates itself and calls `onChange`).
- Reload the shared draft before mounting and call `setPathway` / `setPublished` when the host refreshes them, so the editor never works from a stale copy. The service refuses a draft saved against an old `draftVersion`.

## Publishing and `effectiveFrom`

The editor calls `stampPublishTime(pathway, published, nowIso)` immediately before `adapter.publish`. It sets `effectiveFrom` on each requirement policy version the published revision does not have yet, and leaves every other policy alone. The shared service does not set `effectiveFrom` itself, and the engine treats a missing one as "from the moment it is evaluated", so stamping at publish is what makes a later replay of student evidence deterministic. Keep it. If the host publishes some other way, it must call `stampPublishTime` first.

## Two things to settle in the redesign

1. **The older per-skill policy dropdown.** The existing pacing editor lists every policy in `pathway.policies[]` as a choice for each skill, which will now include the requirement policies by their labels ("Class defaults · 30 questions at 90%"). Picking one there by hand is overwritten the next time requirements are edited here, because the checkpoints are re-pointed at the most specific level. Recommended: in the redesign, hide `policy:req:*` policies from that dropdown (or show them read-only) and send teachers to the requirements editor for them. Policies from the older editor stay selectable and are respected here as skill-level choices.
2. **The older per-area policy form.** It creates policies with ids like `policy:<areaId>`. Those are treated here as older-editor policies and left alone. Decide whether to retire that form in favor of this editor; nothing here removes it.

## What a host may rely on

- `pathway/requirements/index.mjs` is the one public entry point of the logic (68 exports). Operations take a pathway and return a new one with `{ ok, pathway, errors, warnings, changed, kept, problems }`; they never mutate their input and never throw on bad input.
- `reviewRequirements(draft, published, graph, { facts, acknowledged })` gives the review screen's data and `readiness.canPublish`, so a host that builds its own screen can still use the same rules.
- `studentRequirementView(progress)` is the student display contract (`PROGRESS_CONTRACT.md`). `previewStudentStates` is the teacher's preview of it.
- `buildContentFacts({ graph, registry, extra })` supplies what the repository can verify about each skill. Add `extra[nodeId].bankSize = { value, basis: 'verified' | 'estimate', expandable }` once a lab can report its question-pool size; the checks that need it are already built and tested.

## Connecting students to the requirements (the next steps, not done here)

This package makes the requirements a teacher can set and publish, and shows what they mean. Measuring real students against them is the engine's job and still needs the steps listed in `reports/mastery-engine/INTEGRATION_HANDOFF.md`: reading practice evidence into the engine on the server, persisting attempt histories (a separately approved migration, not created here), recording restarts with a server clock, and showing `studentRequirementView` on the student sidebar and map. Until those exist, a published requirement is stored and shown to teachers but does not yet drive a student screen.

## Trust boundary, unchanged

Browser practice stays provisional. The component and the logic produce no award, no standards score and no verification, and the student view says that meeting a requirement is a practice milestone. Official awards still come only from `proposeAward()` in `mastery/award.mjs`, which is server-only, needs every counted event verified, is not exported from any browser entry point, and is not imported by anything in this package (a test checks that). The absence of a trusted evidence source still prevents an official mastery award.
