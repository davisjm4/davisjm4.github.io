# Implementation report: teacher-controlled mastery requirements

A teacher can set how many questions students must answer and how accurate they must be, for a whole class, for a learning area, or for one skill. The tool says in plain words what that asks of a student, warns when a requirement cannot be met, keeps every published version, and measures students with the same arithmetic the mastery engine already uses. Nothing here has been merged, deployed, published to students or activated.

## How the requirements fit the structures that already exist

A requirement is not a new kind of record. Each level that has settings is **one ordinary versioned pathway policy**, and each skill's checkpoint already points at a policy by id and version:

| Level | Policy id | Used by |
| --- | --- | --- |
| Class defaults | `policy:req:class` | every skill with no area or skill setting |
| One learning area | `policy:req:area:<areaId>` | every skill in that area with no setting of its own |
| One skill | `policy:req:skill:<nodeId>` | that skill |

A checkpoint is pointed at the most specific level that exists: the skill, else its area, else the class, else the provisional policy that means "nothing set". The class defaults are therefore stored once, not once per skill: a 123-skill class with only class defaults has one requirement policy. No permanent policy is ever created for skills the teacher did not touch.

Each policy records, in a small `requirementSource` note, which settings **that level chose itself**. The rest of its values are copies of what it inherited, written so the engine and the existing pathway code see a complete policy. Those copies are derived: every operation re-derives all of them from the explicit choices, and a consistency check flags any copy that has drifted. So there is a single source of truth (the explicit choices) and the stored copies cannot silently disagree with it. See `RESOLUTION_AND_VALIDATION.md`.

## What a teacher sees and can do

**Simple settings.** Minimum questions (a whole number), required accuracy (typed as a percentage, never `0.90`), and an expandable Advanced section holding minimum correct answers, difficulty levels, question variety, and how skipped, revealed or hinted questions are treated. Every change is explained as it is typed, for example: *Students must answer at least 50 questions with at least 95% first-attempt accuracy. At 50 questions, students need at least 48 correct answers. That allows up to 2 mistakes in the first 50. Students may answer more than 50 questions to improve their accuracy.*

**Three levels, with the source shown.** Each value shows where it came from (class defaults, this learning area, set for this skill). A level can be restored to inherited, one setting or all of them, after a confirmation.

**Bulk editing.** Apply to all class skills, to selected areas, or to selected skills; copy an area's own settings to other areas; remove every skill override inside chosen areas; reset to inherited; review all overrides in one table. A bulk edit keeps a skill's own settings by default and says which skills it kept; replacing them is an explicit choice.

**Presets.** Quick Recognition (50 at 95%), Standard Practice (30 at 90%), Complex Reasoning (20 at 90%) and Custom. They only fill the two editable numbers, they are labeled as starting points that have not been calibrated against student data, and editing a number turns the label into Custom. The numbers come from the one list already in the engine (`mastery/suggestions.mjs`), so there is nothing to keep in step.

**Warnings that distinguish what is known from what is guessed.** Each finding says whether it is a verified limit or an estimate, and each lands in one of four states: fine, worth knowing (warning), can be saved as a draft but not published, or cannot be saved. See `RESOLUTION_AND_VALIDATION.md` for the exact rules.

**Draft, summary, explicit publish.** Edits go to a draft. The Review tab shows a table of defaults and overrides, a plain-language list of what changes compared with the published version, every problem grouped under a plain heading, and a Publish button that stays off until the draft is publishable. Publishing creates new policy versions and stamps their effective time; earlier versions are never edited or removed.

**A preview of what students see.** The Class defaults and skill forms show sample student screens (just starting, partway, one answer short, requirement just met) produced by running synthetic answers through the real engine.

## How it keeps teachers and students measured the same way

All accuracy arithmetic goes through the engine's integer basis-point functions (`minCorrectFor`, `percentToFraction`, `formatPercent`, `toBasisPoints`). The teacher's sentence "students need at least 48 correct answers", the preview's "just met" sample, and a real student's progress object all come from that one place. A test checks the sentence against an independent integer calculation for every question count up to 250 at several percentages, and another checks that the preview's "just met" sample meets the requirement in the real engine while one fewer correct answer does not, for every preset.

## Quantity semantics, as implemented

- Each question counts once, by the student's **first** answer. Retrying never adds credit, and a wrong first answer stays in the total.
- Questions from focused practice and from Mixed Practice both count toward the skill they test, once.
- Skipped, revealed and hinted questions are never counted as correct. By default they stay in the denominator as incorrect; the teacher may instead leave a limited share out.
- If a minimum number of correct answers is set, it is required **in addition** to the accuracy: both must be met.
- A student may answer more than the minimum to raise their accuracy. The same attempt continues until the requirement is met; a restart is a choice, not a requirement.
- Meeting a requirement is a **practice milestone**. It never sets the 0 to 4 standards score, never creates an award, and is never labeled verified. The score comes from the teacher's own assessment.

## Boundary conditions, and how each is met

| Boundary | How it is met |
| --- | --- |
| Do not modify production `main` | Work is on `claude/teacher-mastery-requirements`; nothing merged. |
| No permanent policies for all 290 nodes | Policies exist only where a teacher set something; class defaults are one policy. A test checks that untouched skills get none. |
| Do not adopt the audit's 80% and 85% | No default is applied. The three presets are the teacher's 50/95, 30/90 and 20/90 starting points, labeled uncalibrated, and nothing is selected until the teacher chooses. |
| Browser correctness is not certification evidence | The component and logic produce no award, no score and no verification. Browser practice stays provisional; the student view says so. |
| No Worker authorization changes or client-side certification | No Worker, route or authentication file is touched. The award module is not imported by any file here, and a test checks that. |
| No new D1 migration | None. Requirements live in the existing pathway policies. |
| No official award without a trusted evidence source | Unchanged: `award.mjs` stays server-only. |
| Do not modify published pathway snapshots | A published policy version is never edited; the first change creates the next version. Curriculum snapshots, schedule and sessions are untouched, and tests check each. |
| No graphical map, no competing LMS | Neither is built. |
| A completed challenge does not award a 4 | The student view always says the score comes from the teacher, and a test checks `standardsScore` is never raised. |
| No secrets or real student records in tests | All tests use synthetic students and the committed graph. |

## What is deliberately not done

- No requirement is attached to any real class or skill. The demo page runs two synthetic practice classes and keeps everything in the page.
- The Teacher Tools redesign was not overwritten. The editor is a standalone component with a documented adapter, so it can be mounted into the redesigned pathway editor (see `INTEGRATION_HANDOFF.md`).
- Topic, difficulty and variety rules are not simulated in the student preview; the preview says so.
- The repository records no question-pool size for any skill, so the "pool smaller than the minimum" check is built and tested but only fires when the host supplies pool sizes (`buildContentFacts({ extra })`). Until then the tool says nothing about pool size rather than inventing a number.
- Question generators and their anti-repeat protections are not touched, and no question families are invented to make a requirement look possible.
