## Integration points, in the order to do them

**1. Policies in the pathway.** A mastery policy is the stored pathway policy plus an optional `challenge` block, so it already fits `pathway.policies[]` and checkpoints already reference it by `policyId` and `policyVersion`. Use `validateMasteryPolicy()` in the teacher editor and on publish (it returns errors and warnings and never throws), `toPathwayPolicy()` to store, and `assessSupport()` to warn about requirements that cannot be met (also useful for the teacher-facing requirement settings). Publish a new version rather than editing one; the engine refuses to judge students against an edited version. Do not modify published curriculum snapshots; none of this touches them.

**2. Reading practice evidence.** `readProfileEvidence()` in `wpr-games/workplace-readiness/service/profile-evidence.mjs` currently returns only assessment evidence. Add a read of the student's practice rows (`performance_events` where `kind` is the practice kind, which `cleanGameAttempt()` writes) and pass them as `rawEvents`. The engine accepts the stored row shape as it is and recomputes node attribution from the graph, so rows stored before Phase 2's new nodes existed attribute correctly without a data backfill. It ignores the stored `n`, `c` and `dimensions` tallies.

**3. Computing progress.** Call `pathwayProgress({graph, pathway, profileId, rawEvents, histories, now, trustResolver, assessmentEvidence})` with the published plan from `publishedPlan()`. It returns every node and area plus the updated histories. `profilePathway()` and `studentContract()` can carry the result as an additive field; `studentContract()` itself needs no change. The scope is derived from the pathway's class, and histories from another student or class are refused.

**4. Persisting histories.** Attempts are derived from evidence, but restarts, awards and the exact moment a policy took effect are not recoverable from evidence, so persist them. A proposed design for a later, separately approved migration (nothing here creates it): an append-only attempts table keyed by attempt id (profile, class, node, sequence, policy id, version and digest, status, window start, open and close times, close reason, snapshot JSON), an idempotency table keyed by restart request id, and an awards table. Write only from server code that re-derives the history from stored evidence and compares it. Set `effectiveFrom` on every published policy version (the revision's publish time) so replays are deterministic.

**5. Restart.** A student asks for a restart; the server records it with its own clock and a client-generated request id, calls `restartAttempt()` with the evidence it read itself, and persists the result. Pass `expectedAttemptId` from the screen the student was looking at so a stale click is refused. Never accept an attempt, a window or an award from the browser.

**6. The trusted-evidence boundary.** Browser events stay provisional: `normalizeEvents()` marks them verified only through the `trustResolver` the server passes, and ignores any trust field on the record. Decide the trusted source with the teacher (see decision 13 in `TEACHER_POLICY_DECISIONS.md`), then build it server-side. Official awards come only from `proposeAward()` in `award.mjs`, which needs every counted event verified and a boundary object covering them. It is not exported from `mastery/index.mjs`, and must be imported only by authenticated Worker code, never by a page. It cannot check an attestation cryptographically, so the route that calls it is the security boundary. An award record has the shape `evaluateNode()` already recognizes, so existing completion logic sees it.

**7. Displays.** The sidebar and learning map read `nodeProgress()` and `areaProgress()` output only (`PROGRESS_CONTRACT.md`). Show `explanation.text`, never identifiers; label policies with `exampleOnly`; treat `verification: provisional` as a practice milestone. Pacing comes from `pacingStatus()` and the standards score from `standards.score`; do not merge them with challenge status.

**8. Record skips.** The practice pages send no event when a student skips or reveals. The denominator rule for those cases only applies to records that carry the flags. A server-side "question presented" record (written when the Worker hands out or the page reports a question) would let the engine count skips; this is optional, and the limitation is stated in every evaluation.

**9. Question variety.** Family-diversity requirements can be verified for 54 of 290 skills today. Strengthening the rest means having each lab report a reasoning family per question and binding it in `build-graph.mjs`, then regenerating the graph and the gap registry (see `MASTERY_ENGINE_DESIGN.md`). Do that before asking for variety requirements, and bump the graph version with a snapshot migration only if ids change.

## Rules for whoever continues

Do not attach any policy to a node without the teacher's decisions in `TEACHER_POLICY_DECISIONS.md`. Do not adopt the audit's 80% and 85% figures. Do not let a browser create an attempt, a restart or an award. Keep node, family, policy and attempt ids stable. Do not hand-edit `curriculum-graph.json`. Do not edit a published policy version; publish a new one. Do not compare accuracy with floating-point arithmetic; use `arithmetic.mjs`, which both student progress and teacher previews already share.
