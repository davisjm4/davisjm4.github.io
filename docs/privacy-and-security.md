# Privacy and security

## CSG-SEC-01 — Identity and authority

**Approved · implemented in the existing service. Roles:** guest, enrolled, teacher, operators. Guest use requires no account. Students use generated pseudonymous IDs with separate invite, recovery and session credentials. Keep any name mapping in a teacher-managed system. Teacher authentication and class ownership are verified server-side for all reads, writes and aggregates. Keep existing production Google authentication and allowlist. The Worker rejects expired, revoked, unauthorized or cross-class credentials.

**States/data:** anonymous, invited, enrolled, session valid/expired/revoked, class archived, denied. Keep credential material out of logs, URLs that leave the browser, exports, screenshots, repositories and audit evidence. Preserve documented hashing, session and retention boundaries. Current profile sessions expire after 30 days, classes after 365 days, and archive immediately closes enrollment and access with the documented retention period. Use the [profiles runbook](../wpr-games/workplace-readiness/service/PROFILES.md) for operational details. **Dependencies:** existing Worker/D1 and profile flows. **Accessibility:** accessible denial, renewal and recovery with no disclosure of another profile. **Acceptance:** test two teachers, two classes and expired/revoked sessions. The wrong principal gets no student data and cannot modify anything.

## CSG-SEC-02 — Practice/report isolation

**Approved · implemented in part. Roles:** all. Keep independent browser state, enrolled sync, and anonymous diagnostic aggregates separate. Use only required data. Preserve current small-group suppression, including existing under-five anonymous submission protection. Imported local data remains provisional. Optional printed student identity stays local and never enters exports of technical evidence, backups, anonymous reporting or server sync. The printable artifact itself can contain the user-supplied name. Synthetic local environments use disposable data and temporary credentials. Production uses real authentication and no local bypass.

**States/data:** scope-selected, local, queued, synced, anonymous aggregate, suppressed, reset and recovered. **Dependencies:** CSG-STU-01/02, CSG-SES-01/02. **Accessibility:** plain scope and storage notices at point of use. **Acceptance:** guest practice, backup, print and reset do not touch class evidence, test identities cannot authenticate in production, and small-group totals cannot be exposed through an export.

## CSG-SEC-03 — Assignment authorization and audit history

**Approved · planned. Roles:** authorized teachers, enrolled students, operators. Reuse existing authorization. Only a teacher with authority for the class may create, edit, end, or release its assignments or restrictions. Validate targets and recipients within class and course scope. Store pseudonymous identifiers and actor/action provenance for creation, change, release and end. Include timestamps and previous/new references. Avoid collecting names, school identifiers, behavior notes or optional sensitive information. Restriction reasons are optional and scoped to the intended audience.

**States/data:** permitted, denied, scheduled, released, idempotent replay and conflicting update. Separate audit history from practice and grading evidence. Propose retention aligned with existing class lifecycle and review it before migration (CSG-OPEN-10). **Dependencies:** CSG-TDL-01/03/04. **Accessibility:** safe, actionable errors and release confirmation with no cross-class disclosure. **Acceptance:** test altered class/recipient IDs, stale edit, overlapping grants and bulk release. Wrong teachers cannot read the grant or infer who received it. An enrolled student receives only their relevant assignment state.
