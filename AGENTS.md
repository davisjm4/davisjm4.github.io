# CS Games contributor instructions

For CS Games work, read [the specification index](docs/README.md) and [development and validation](docs/development.md) first. Read the domain documents linked from the index for every affected requirement. For teacher-directed learning, read the [assignment contract](docs/teacher-directed-learning.md), [student experience](docs/student-experience.md), [teacher experience](docs/teacher-experience.md), [mastery rules](docs/mastery-and-evidence.md), and [acceptance scenarios](docs/acceptance-tests.md) together.

This branch contains a review draft. Product decisions marked approved come from the product owner. The specification baseline and proposed designs require separate approval. Scope authorization for implementation, data migration, publication, and deployment comes from the current task. In particular, the specification draft is documentation-only.

Before editing, identify the affected requirement IDs, current entry points, shared owners and compatibility risks. Reuse shared navigation, identity, evidence, reporting and UI contracts. Preserve deployed links, stored records, source attribution, and role boundaries. Record unresolved policy conflicts in [the decision log](docs/decisions.md) and request a product decision before changing behavior that depends on one. Record test results by requirement and environment. Use synthetic data for authenticated walkthroughs.

These product instructions apply to CS Games, its Java and AP CSP games, Workplace Readiness, RACECES, Robotics, Teacher Tools, and their shared backend. Preserve the scope of unrelated portfolio and classroom materials in this repository.
